PLD / cumplimiento — how it works today

Snapshot of the shipped feature (not the target KYC form). Open this file in a browser. Two people are involved: an org operator (member with organization-compliance-access) and a PLD invitee (counterparty user with no organization).

Built and wired Built but incomplete / unused by invitee Not built (data + document collection UI)

1. Access gates

Org switch

  • Organization.pld_access_enabled (Django admin)
  • Without this, entity APIs and the assistant return 404

Operator capability

  • Flag organization-compliance-access
  • Owners get it automatically; members need it on a role
  • Sidebar “Cumplimiento”, /compliance, assistant

Invitee

  • Not an org member (profile.organization = None)
  • No chat, no hub
  • Login home is /pld/expediente

Member with no role

  • Has an org, no role capabilities
  • Login home is /no-role
  • Not a PLD invitee

4. Data model as implemented

erDiagram
  Organization ||--o{ PLDEntity : has
  Organization ||--o{ PLDExpedient : has
  Organization ||--o{ PLDInvite : has
  Organization ||--o{ ComplianceFolio : "assistant uploads"
  PLDEntity ||--o| PLDExpedient : "one per org+entity"
  PLDEntity ||--o{ PLDInvite : invites
  User ||--o{ PLDEntity : "invitee link optional"
  User ||--o{ ComplianceFolio : subject_user
  ComplianceFolio ||--o{ FolioDocument : docs

  Organization {
    bool pld_access_enabled
  }
  PLDEntity {
    uuid id
    string person_type
    string relationship "null = org self-entity"
    string email
    json metadata "name / legal_name / rfc stub"
    fk user "set on invite accept"
  }
  PLDExpedient {
    uuid id
    string status "always data_collection at create"
    string vulnerable_activity "unused in UI"
  }
  PLDInvite {
    string email
    string status
    datetime invite_expires_at
    fk accepted_user
  }

PLDEntity.metadata is a JSON field validated by Pydantic (PersonaFisicaMetadata / PersonaMoralMetadata): name or legal_name, rfc, economic_activity, and a thin controller object. There is no separate “intake answers” table. Folio models are a second stack used only when files are uploaded on the operator compliance chat.

5. Two stacks that are not joined

Counterparty expediente Compliance assistant + folio
Who uses it Operator hub + invitee “Your file” Operator with PLD + provisioned agent
Primary records PLDEntity, PLDExpedient, PLDInvite Sticky Conversation (surface: compliance), ComplianceFolio
Status Create / invite / accept / list status Chat + file ingest to folio; not shown on expediente
Invitee can do See status badge only Nothing — no chat access

6. Screens and APIs

Route / APIWhoWhat it does now
/compliance Operator Hub: counterparties, optional self-entity card, link to assistant
POST /v1/compliance/entities/ Operator Creates entity + expedient in data_collection
POST .../entities/{id}/invite/ Operator Email with /signup?pld_invite=
/signup?pld_invite= New invitee Creates user without org, accepts invite, then login → expediente
/pld/invite?token= Existing user Accepts invite, sets entity.user
/pld/expediente Invitee Lists files + status. No form, no uploads
GET /v1/compliance/my-expedients/ Invitee Entities where entity.user is the current user
/compliance/chat Operator Sticky assistant thread; 404 if agent not provisioned

7. What is explicitly not in the product yet

Data collection form

  • Invitee cannot submit Anexo 3 / 4 fields
  • Hub create form only stores display name + email + type
  • Expedient stays in data_collection forever

Document collection

  • No invitee upload UI
  • Folio ingest only from operator assistant chat
  • Folio is not linked to PLDExpedient

Self-entity

  • Unique relationship = null row per org
  • Shown on hub if it exists
  • No dedicated create flow in the hub

Statuses after data_collection

  • Enum exists: document_collection, cross_reference, waiting_sign, signed, delivered, action_required
  • Nothing in the app advances them
